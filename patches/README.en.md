# dshui Source Patch

> English · [中文](README.md)

`dshui-bundles.patch` contains the dshui modifications to the source of
[deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) (59 files, ~195 KB: the client
bundles and the host runtime, based on dsh `0.2.1-rc.3`). The client and the host must be **aligned**
to the same base commit and applied together, so they are merged into a single patch — applying only
half is incomplete.

## Client bundles (browser SPA)

- `ui-workspace`: `tree.ts` (`scopedWorkspacePath`, the `scope` / `deletedSessionIds` params on the
  derives, cwd-based scope filtering, and the locally-deleted-session hide set),
  `WorkspaceBrowser.tsx` (`scopedWorkspacePath` / `useDeletedSessions` wiring, deleted-row hiding),
  `contract/slots.ts` (`DeleteSessionInjected` and the `deletedSessions` observable), `index.ts`
  (the dshui deleted-sessions snapshot store plus `deleteSession`: requests the extension host —
  through the webview shell — to delete the session log and records the id in the local hide set),
  `session-actions/DeleteSession.tsx` (since 0.1.7 upstream moved the session row actions into slot
  entries: this file registers "Delete Session" into `sidebar.workspaces.session.menu.item`
  (order 450) and `sidebar.workspaces.session.row.action` (order 300), beside the stock
  archive/pin entries), `locales.ts` (adds `menu.deleteSession` / `actions.delete`), and
  `tsdown.config.ts` (bundle id → `dshui-client-ui-workspace`);
- `ui-conversation`: `apply.ts` (when a second shared-backend window re-binds a session the
  `conversation` service may read `undefined` — the old implementation threw and abdicated the
  composer slot once with no retry, permanently vanishing the composer until a window reload; it
  now degrades to the absent posture, and the next binding re-resolution restores the live
  composer), `skeleton/dshui-scope.ts` (since 0.1.7 upstream split the conversation skeleton into
  ConversationRoot/MainPanel/Content, so the `SCOPE` constant became its own module: `DSHUI_SCOPE`),
  `skeleton/ConversationMainPanel.tsx` (the `data-dshui-scope` root marker),
  `skeleton/ConversationContent.tsx` (static chip, hero hiding, a scope-kept composer),
  `skeleton/EmptyHero.tsx` (the `staticChip` prop of `WorkspaceChip`),
  `ConversationRoot.module.css` (scoped hero pinned to the bottom, composer kept during `settling`),
  `HeroShell.module.css` (`.workspaceStatic`), and `tsdown.config.ts` (bundle id →
  `dshui-client-ui-conversation`);
- `ui-chat`: `chat/MessageItem.tsx` (the user-message renderer is split into `UserMessageNodeView`
  and `SteeringMessageNodeView`; a user message renders a `conversation.chat.user-actions` action
  strip anchored to its Turn inside the IconActions row, while a steering message does not. Since
  rc.2 upstream renders the user-message body through a factory slot
  (`conversation.chat.user.content`) and the body text through a rule/`conversation.user.text` →
  `conversation.user.text.node` chain, so the link projection moved down to that text layer) —
  `chat/user-link-rule.ts` (`link` rule: claims `[label](destination)`; an allowlisted
  http/https/mailto URL is left to the renderer, a destination `new URL` cannot parse becomes a
  file button, and the `#L10` / `:10` suffix — including `-L20` and en-dash ranges, of which the
  first line is kept — is split off by `filePathAndLine` into the open gesture's `line`; any other
  absolute URL is not claimed and stays literal), `chat/UserLink.tsx` (anchors for external URLs,
  buttons for files, opened through the injected `openFile`), `chat/register-user-links.ts`
  (registers the rule on `uiConversation.userText` and the `link` renderer into
  `conversation.user.text.node`; `openFile` goes through `remote.session.openWorkspacePath` with
  `dshuiOrigin` / `dshuiLine`), `dshui-open.ts` (`dshuiClickOrigin` / `dshuiOpenPath`, shared with
  `apply.ts`'s ChatView `openFile`), `apply.ts` (the view's `openFile` routes through the Host into
  the VS Code editor instead of upstream's in-product `dsh-resource://` preview),
  `chat/MessageItem.module.css` (the `.link` styles), `chat/register-node-renderers.ts` (the `user`
  registration declares the `conversation.chat.user-actions` child slot), `contract/slots.ts`
  (`UserActionOwnerProps` and the `conversation.chat.user-actions` slot declaration), and
  `tests/user-link.client.spec.tsx` plus the small spec adjustments the split needs;
- `packages/extensions/cordis-client-runner/src/client/slot-catalog.ts`: regenerated by
  `pnpm run gen-client-catalog`, cataloging the `conversation.chat.user-actions` slot entry (shown
  in the chat "slot catalog" docs).
- build preset: `packages/client/tsdown.client.ts` (since rc.2 `clientBundle(packageDir, …)` reads the
  bundle id from the directory's `package.json` name; a dshui profile row name is not a package name,
  so the preset gains a `pluginId` option and both `tsdown.config.ts` files pin their
  `dshui-client-*` id through it).

Effect: the sidebar lists only the current workspace's sessions, the input box stays pinned to the
bottom (no centered hero), the session menu offers "Delete Session" (the extension host deletes the
session log files under `$DSH_HOME/sessions/...` via the VS Code file API, bypassing dsh's archive
RPC; the archive/pin row actions upstream added in 0.1.7 remain available beside it), every user
message carries an extensible action strip (`conversation.chat.user-actions`,
which the extension uses to mount "Rollback"), and markdown links in user messages are clickable
(external URLs open in the system browser, relative paths open the file in the current window). Chat
file links open in the host VS Code (darwin: local open bridge → `code` CLI → `vscode://file`, no
system dialog — see the host side below). At runtime the **prebuilt artifacts** at
`../dshui-plugins/*/client.js` are used; this patch exists to reproduce those artifacts from source.

> The specs keep only the small adjustments needed to compile and preserve the existing assertions
> (a `useDeletedSessions` stub, a `renderUserActionsSlot` stub, the `SteeringMessageNodeView` branch,
> and the `userText` member the ui-tool `uiConversation` stub needs now that Chat registers a
> user-text rule).

## Host runtime (server side)

The string patches the extension once applied to the npm package at runtime (see the deleted
`src/openPatch.ts`) are now baked into the source and compiled in:

- `packages/util/native-command/src/path-opener.ts`: when the extension host markers are present
  (`DSHUI_OPEN_ENDPOINT` / `DSHUI_BRIDGES_FILE` / `DSHUI_CODE_CLI` — the extension always injects
  them when it launches the server), the `darwin` branch of `openNativePathWithIntent` tries "local
  open bridge → `code` CLI → `vscode://file`", with new bridge/CLI/URL helpers
  (`dshuiOpenViaBridge` / `dshuiOpenViaCli` / `dshuiVscodeFileUrl` / origin-aware bridge selection),
  so chat file links open in the host VS Code (through the in-extension bridge, no system dialog); a
  plain `dsh` deployment without those markers keeps the stock behavior (`open [path]`, or
  `open -t [path]` for the text-editor intent). `PathOpenerInternals` gains `dshuiOrigin` so the
  click origin takes part in routing, and `dshuiLine` so a link's line travels as the bridge request's
  `line` query parameter (the extension's openBridge turns it into the `showTextDocument` selection).
  The `code` CLI and `vscode://file` fallbacks address a file only and have no line syntax, so the
  bridge path is the one that consumes a line.
- `packages/client/connection/src/browser-auth.ts`: both index 303 redirects (the token exchange and
  the "cookie authenticated, token mismatch" case) keep the `dshui_workspace` / `dshui_theme` query
  params besides `launch` (upstream 0.1.7 answers a bare directory-relative `./`, which drops the
  scope too), so a shared-backend window whose token went stale does not silently adopt the server's
  own working directory.
- `packages/api/session-controller/src/commands.ts`: a `session.fork` child now runs `inbox.clear()`
  right after creation, discarding the **pending queue** it inherited from the source seed (the
  dangling next-turn / next-step `agent/inbox/spliced` inserts). Previously, forking a session whose
  last turn had completed but which still held a queued message handed that message to the child as
  live input: the user's first send in the child ran the source's queued message and the message the
  user had just typed stayed pending behind it. The inherited pending input is recorded as canceled
  events; the source keeps its queue, and a child with nothing pending appends no event. The patch
  also updates `tests/session-fork.host.spec.ts` (a new "child inbox is empty" case) and
  `tests/commands-create-fork.host.spec.ts` (the fake Agent gains an `inbox`).
- `packages/api/session-controller/src/index.ts` and `.../src/types.ts`: the `openWorkspacePath`
  request carries `dshuiOrigin` and `dshuiLine`, which are threaded into the opener internals (since
  0.1.7 the opener
  also has the `openNativeAssociatedPath` / file-application branches; the dshui call sites are
  aligned with them). `dshuiLine` is a link's line: the upstream markdown renderer strips a
  `#L10` / `:10` suffix into its own `openFile` option rather than leaving it in the path, so the line
  can only travel as a request field; native-command turns it into the bridge's `line` query
  parameter, and the extension's `showTextDocument` selection lands on it. The regression case is
  "threads the dshui requested line into the opener internals" in
  `tests/session-open-workspace-path.host.spec.ts`. `verifyDesktopPath` expands `~` through
  `dshuiHomePath` before validating: the
  browser cannot read the account home, so a home link arrives in its `~` spelling, and a bare
  `resolve` would staple it to the server's working directory (`<cwd>/~/.dsh/...`).
- `packages/api/settings-controller/src/index.ts`: `openSettingsDocument(dshuiOrigin, signal)`
  threads the click origin the same way (since 0.1.7 SettingsController keeps only `openTextFile`).
- `packages/client/ui-chat/src/client/apply.ts` and
  `packages/client/ui-settings-general/src/client/settings-document-store.ts`: the client attaches the
  window scope (`__DSHUI_WORKSPACE__` or the `dshui_workspace` query param) to those two remote calls.
  The former's `dshuiOpenPath` also owns the file-link destination spelling (workspace-relative →
  session cwd; home-relative → `~` kept after dropping `./`/`../` prefixes), and sends the upstream
  `OpenFileOptions.line` along as `dshuiLine` — upstream's `ChatView` always passed a line to
  `openFile`, and the dshui reroute of the open path lost it, so a line-numbered link opened the top of
  the file. Links inside a user message are rendered by dshui's own `MessageItem.tsx` projection
  (above), which splits the same `#L10` / `:10` suffixes and hands the line to `openFile` as well.
- `packages/mcp/mcp-client/src/index.ts`: adds the `startup: 'eager' | 'lazy'` option (default
  `eager`). In `lazy` mode activation returns immediately and the supervisor connects and registers
  tools in the background, so a slow remote (for example one behind OAuth) never delays dsh startup;
  the READMEs and a few specs are updated alongside.

These packages are filled into `node_modules/@deepseek-ai/*` from the **source-built artifacts**
by the extension's `scripts/sync-dsh.mjs`, instead of being downloaded from npm. The root
`package.json` declares only **one** anchor dependency `@deepseek-ai/dsh` (the rest of `@deepseek-ai/*`
are transitive deps in its manifest, so `npm list` accepts the whole closure without fetching from
the registry — the source artifacts are already in place). The runtime reads the **prebuilt artifacts**
in `node_modules/@deepseek-ai/*`; this patch reproduces them from source.

## Applying (the base commit is pinned)

The patch targets this base commit (**pinned; it must not drift**) — the dsh `0.2.1-rc.3` release
merge (tag `dsh-v0.2.1-rc.3`):

```
1f81c047fc48fa190a683e469daa699857e9afe8
```

```sh
git clone https://github.com/deepseek-ai/deepseek-harness.git .dsh-src
cd .dsh-src
git fetch origin 1f81c047fc48fa190a683e469daa699857e9afe8 && git checkout FETCH_HEAD
git apply --3way ../patches/dshui-bundles.patch     # fails safely if the base commit mismatches
pnpm install                                        # requires pnpm 11.7.0, Node ^22.19 || >=24
pnpm run clean                                      # REQUIRED on a rebase: drop the previous
                                                    # version's lib/ and tsbuildinfo
pnpm run build:lib:host
pnpm run build:lib:client
pnpm run build:web                                  # browser shell (missing it fails every client plugin)
pnpm run gen-client-catalog                         # regenerate the slot catalog
cd ..
node scripts/sync-dsh.mjs                           # copies the @deepseek-ai/* source artifacts into node_modules
node scripts/copy-clients.mjs                       # copies the two UI bundles into dshui-plugins/ (asserts the bundle id)
npm run compile
```

> Use `git apply --3way` when moving to a new base: the three-way merge marks only the genuinely
> conflicting hunks. The 0.2.1-rc.2 → 0.2.1-rc.3 move touched 640 upstream files, yet only 4 intersect
> this patch (`ui-conversation/src/client/apply.ts`,
> `ui-conversation/src/client/skeleton/ConversationRoot.module.css`,
> `ui-workspace/src/client/navigation.ts`,
> `extensions/cordis-client-runner/src/client/slot-catalog.ts`); all four applied cleanly, and
> `slot-catalog.ts` was then regenerated by `pnpm run gen-client-catalog`.

### Re-exporting the patch

Re-exporting must use **`--binary`** (`make dsh-gen-patch` already does):

```sh
git -C .dsh-src diff --binary <base commit> > patches/dshui-bundles.patch
```

- **`--binary` is not optional.** The base snapshot adds PNG/ICO binary assets; without the flag
  `git diff` writes only a `Binary files /dev/null and b/... differ` placeholder (with **no content**),
  and `git apply` then reports `cannot apply binary patch ... without full index line` and rejects the
  whole patch. Every current dshui change is text, but any binary asset in the base snapshot trips
  this, so always export with `--binary`.
- **The base commit must move with the rebase.** `DSH_BASE` (Makefile) and the SHA in this file must
  equal the commit the export used. A patch exported against a stale base swallows the entire
  upstream delta (the rc.1-based export was 3447 files / 15.2 MB) and becomes unusable; a correct
  export stays at 59 files / ~195 KB.
- **Do not export with a `cd` recipe.** `make dsh-gen-patch` uses `git -C $(DSH_SRC)` plus an
  absolute output path. The earlier form — `cd $(DSH_SRC) && git diff … > "../patches/…"` inside a
  brace group — truncated the patch to an empty file first and only then reported the failed `cd`,
  silently destroying the patch.

> `pnpm run clean` is mandatory when rebasing onto a new base: the previous version's stale typert
> remote declarations left in each package's `lib/types` and `*.tsbuildinfo` otherwise make `tsc -b`
> reuse them, producing dozens of bogus "remote method does not exist" errors.

## When Upstream Drifts

A failed `git apply` means the base commit has drifted — re-apply each change per the checklist in the
main [README, section "Upgrading with dsh Releases"](../README.en.md#upgrading-with-dsh-releases) (the
changes are small; follow the comments in each file). dsh is MIT-licensed, so this patch and its
artifacts may be freely modified and redistributed as long as the upstream copyright notice is kept.

### Upstream specs that are always red under the overlay (not regressions)

`pnpm run test:gui` (`vitest run packages/client packages/host`, 653 files / 10919 cases) leaves 3 failing
files (3 cases) once this patch is applied; the other 649 files / 10913 cases pass (1 skipped). Every one of them is the necessary
consequence of the overlay deliberately changing upstream behavior — do not chase them as rebase
regressions:

| Spec | Cause |
|---|---|
| `packages/client/ui-tool/tests/toolview-slot.client.spec.tsx` | Upstream 0.2.x opens files in the in-product right Sidebar (it asserts `sidebarRight.openResource('dsh-resource://file/session/…')` is called and `openWorkspacePath` is **not**), while dshui's `ui-chat/apply.ts` routes `openFile` through `remote.session.openWorkspacePath` so the hosting extension opens the file in the VS Code editor — the whole point of this extension |
| `packages/client/ui-tool/tests/chat-ptc-subcalls.client.spec.tsx` | Same, along a second file-path click route |
| `packages/client/ui-theme/tests/radius-styles.client.spec.ts` | dshui's `ui-conversation/src/client/skeleton/HeroShell.module.css` sets `.workspaceStatic { border-radius: 16px }`, which is absent from `ui-theme/tests/expected/radius-exceptions.expected.json`. To clear it, switch the value to a `--dsw-radius-*` token or add the exception to that expected file |

Three environment traps met while running the gates locally:

- **`packages/util/native-command/tests/path-opener.spec.ts` is falsely red inside a dshui-hosted
  shell**: it inherits `DSHUI_OPEN_ENDPOINT` / `DSHUI_BRIDGES_FILE` / `DSHUI_CODE_CLI`, so
  `dshuiHosted(process.env)` is true and the darwin branch takes the bridge/CLI route while the spec
  mocks `node:child_process`'s `execFile` to never call back — 5 cases time out at 5s. Re-run with
  `env -u DSHUI_OPEN_ENDPOINT -u DSHUI_BRIDGES_FILE -u DSHUI_CODE_CLI` and it is 60/60.
- Client specs run on the source plane (tsconfig paths), but `client-bundle`-style specs read the
  `lib/client.js` artifact, so `pnpm run build:lib:client` must have run in `.dsh-src` first.
- **`packages/client/connection/tests/binary-rpc.host.spec.ts` is falsely red under full parallel load**:
  its two "preserves … through the HTTP bridge" cases each start a real HTTP server and hit the 5s
  timeout while 653 files run in parallel; on its own the file is 43/43.
